# Litmus "Tuesday Outage" — Incident Review

Root-cause analysis, causal graph and minimal fix for the Litmus degradation that began at the
Kestrel quarterly release window (Tue 15 Sep 2026 02:00 UTC).

## Repo layout

```
litmus_config.json    # run contract for the evaluation agent
solve.py              # evidence-driven analyser (pure stdlib, no installs)
requirements.txt      # intentionally empty — nothing to pull from Artifactory
Dockerfile            # local smoke test only
root_causes.csv       # deliverable 1 (generated by solve.py)
causal_graph.json     # deliverable 2 (generated by solve.py)
fix_set.json          # deliverable 3 (generated by solve.py)
findings.md           # per-cause evidence dump (generated by solve.py)
```

```bash
python3 solve.py <pack_dir>              # prints the one JSON object the grader reads (stdout only)
python3 solve.py <pack_dir> --out .      # also regenerates the deliverable files above
```

Runtime is about 1 s on the 18,429-span pack. All diagnostics go to stderr.

## Approach Summary

### Result at a glance

| `MODEL_ALIAS_DRIFT` | orchestrator | 2026-09-15T02:43:58Z | `sp_39147c953ac4` | `set_tool_arg_parsing` → `object` |
| `TOOL_RESULT_LIMIT_LOWERED` | extract | 2026-09-15T04:45:01Z | `sp_5c5a9c76e94b` | `set_result_chunking` → `true` |

Five root causes and five operations, one per cause. Every onset is the first post-window span in
which the cause acts on a real Litmus job, not the 02:00 release timestamp. Every evidence span is
that first acting span.

### Method

The rule I held myself to was: a root cause is claimed only if the traces show it **acting on
Litmus after 02:00 Tuesday and never on Monday**. A changelog entry alone was never enough.
Monday 00:00 to Tue 02:00 (115 jobs, 0 failures, $0.608 per job) is the baseline. For each of the
15 codes I wrote a detector in `solve.py` that looks for the specific trace signature Kestrel's
docs predict for it. A detector fires only on a signature that is absent on Monday and present
afterward. It returns the first acting span (evidence and onset), the component where it acts and
the single operation that neutralises it. Symptom edges are added to the graph only when the
downstream effect is itself measured in the traces.

### Root causes: evidence, and proof that Litmus was affected

**1. `MODEL_ALIAS_DRIFT` (orchestrator).** The orchestrator addresses its model through
`kestrel-pro-latest` (overlay ov-01) and parses tool arguments as a string
(`tool_arg_parsing: string`). At the window the alias moved from `kp-2026-02` to `kp-2026-08`,
which returns tool-call arguments as a JSON object (Kestrel docs §1, KCL-043). From the first
post-window job (J1105, 02:43:58) `plan` calls resolve to `kp-2026-08` and fail with
`tool_args_parse_error: "expected JSON string for tool arguments, got object"`. There are 450
failed plan attempts (150 plans × 3 attempts) and **zero on Monday**, when every plan resolved
to `kp-2026-02`. This is the largest single hard-failure driver: about 100 jobs fail at planning,
and re-plans after re-dispatch fail the same way. It matches the PlanArgParseErrors alerts
(10 firings).

**2. `RATE_TIER_DOWNGRADE` (extract).** There are 5,345 HTTP 429 `rate_limited` / "account
request rate exceeded" responses on `extract.fetch_paper`, and **none on Monday**. Each wave of
8 fetches gets about 4 through and about 4 rejected. Kestrel returns `retry_after_ms: 4000`, but
Litmus applies `retry_policy: immediate`: attempts 1 to 5 all land within about 0.3 s (exactly
1,069 requests at each attempt number). Retries exhausted, the orchestrator re-dispatches the
Extract stage (175 `redispatch_extract`, all `reason: rate_limited`), which re-runs the plan and
every already-succeeded fetch. After the second re-dispatch the job fails. The tier change took
effect at 02:00 (KCL-033/048), but the first rejection on Litmus traffic is at 10:13:58, when
daytime volume first exceeded the new allowance, so that is the onset. **Why this is the rate
tier and not the concurrency cap:** there are zero 504 `queue_timeout` responses, `queue_wait_ms`
is null on all 4,714 Extract spans, and the error text names the account rate.

**3. `TOOL_RESULT_LIMIT_LOWERED` (extract).** On Monday, 63 papers larger than 24 KB were
delivered whole (up to 58,660 bytes). After the window, 161 `fetch_paper` results arrive at
**exactly 24,576 bytes**, with `chunk: null` because result chunking is off. Every one is
followed by `extract_findings` failing twice with `json_decode_error: "unterminated string at
byte 24576"`. That is 322 errors, and they explain all 11 ExtractDecodeErrors alert firings. The
jobs still complete, and the paper is counted in `papers_in_context`, so this is a silent
**partial extraction** (a degraded output), not a hard failure.

**4. `CONNECTOR_PAGINATION_CHANGED` (cite_check).** CiteRegistry v2.3 (Monday) returned 18 to 48
records in one response. After the window, v2.4 returns `records_returned: 20`, `has_more: true`,
a `next_cursor`, and the cursor is never followed, because `follow_cursor: null` falls back to the
SDK default of false (KCL-058). As a result, 152 of the 160 post-window reviews are marked
`verdict: verified` with `citations_checked: 20 < citations_total` (for example, 20 of 37 in the
first one). These are **under-verified citations**: silent, and no alert fires.

**5. `REASONING_DEFAULT_CHANGED` (synthesize).** `synthesize.reasoning` was unset by ov-04 ("use
Kestrel default"), and Synthesize is alias-addressed. The default for alias calls changed from
`off` to `medium` (docs §4, KCL-051). `write_review` reasoning tokens go from **0 on every Monday
call to 16,000 on every post-window call**, billed at output price (about $0.24 per review).
Mean call time also rises from 95 s to 161 s. Cost per job, computed from the traces, is $0.603
on Monday and $0.723 / $0.631 / $0.662 on Tue/Wed/Thu. Those figures match FinOps' $0.60 → $0.66.
The rise is held down only because about half the jobs now die before reaching Synthesize. By
contrast, the orchestrator sets `reasoning: medium` explicitly, and its `plan` calls show
2,000 reasoning tokens both before and after the window, so it is unaffected.

### Causal graph (16 edges, direct links only)

```
MODEL_ALIAS_DRIFT → ARG_PARSE_ERRORS → JOB_FAILURES → ALERT_FLOOD
RATE_TIER_DOWNGRADE → RATE_LIMIT_REJECTIONS → IMMEDIATE_RETRY_STORM → STAGE_REDISPATCH
                                                   STAGE_REDISPATCH → JOB_FAILURES | COST_SPIKE | LATENCY_INCREASE
TOOL_RESULT_LIMIT_LOWERED → TRUNCATED_TOOL_RESULT → PARTIAL_EXTRACTION
CONNECTOR_PAGINATION_CHANGED → PARTIAL_CITATION_SET → UNDER_VERIFIED_CITATIONS
REASONING_DEFAULT_CHANGED → REASONING_TOKENS → COST_SPIKE | LATENCY_INCREASE
```

Each symptom edge is backed by a measurement:

- **Re-dispatch causes cost.** Plan cost per job rises from $0.05 to $0.12. Extract cost per job
  stays flat even though only half the jobs finish, because re-dispatch re-runs completed calls.
- **Re-dispatch causes latency.** p95 job time rises from 3.98 to 6.79 minutes.
- **Reasoning causes latency.** `write_review` takes 66 s longer per call.
- **Job failures cause the alert flood.** JobErrorRate (critical) fires every day from Tuesday
  on, with job error rates of 51%, 53% and 51%.

Some edges are omitted deliberately. The count-based alerts (KestrelRateLimited,
PlanArgParseErrors, ExtractDecodeErrors) are not linked into `ALERT_FLOOD`, because that node is
defined as *error-rate* alerts and a wrong edge costs more than a right one earns. No
`QUEUE_TIMEOUTS`, `CACHE_MISSES`, `OUTPUT_LENGTH_LIMIT_HIT`, `SCHEMA_REJECTIONS` or
`FALLBACK_INDEX_USED` nodes appear, because none of those effects occurs.

### Fix: why each operation is needed, and why nothing smaller works

Operations are applied in order from Tue 02:00.

1. **`set_tool_arg_parsing orchestrator object`.** This removes every plan failure. It makes the
   client parse the encoding the alias now returns, and it keeps the orchestrator on the model
   the team deliberately chose. The alternative, `pin_model kp-2026-02`, would also work, but
   that snapshot is supported only until 31 Dec 2026, so it postpones the same break. Pinning
   `kp-2025-11` would be rejected, because that snapshot is retired.
2. **`set_retry_policy orchestrator exp_backoff_jitter`.** This is Kestrel's documented
   recommendation (§7). Immediate retries consume the allowance without succeeding, so
   honouring the 4 s back-off turns the about 4 rejected fetches per wave into successes,
   removes re-dispatches (with their duplicate plan and extract cost and latency), and removes
   the "rate limited after retries" failures. Other options were rejected:
   - `request_rate_tier`: tiers are set by billing agreement, not by API (§7), so this would
     likely be rejected.
   - `set_max_fanout` below 6: this breaches the 20-min SLA (runbook §5).
   - Raising `set_retry_max`: more immediate retries only burn more allowance.
3. **`set_result_chunking extract true`.** The 24 KB cap "cannot be raised" (§6), so
   `set_tool_result_limit` would be rejected. Chunking is the documented remedy, and it removes
   every partial extraction.
4. **`set_follow_cursor cite_check true`.** CiteRegistry v2.3 is retired, so
   `set_connector_version v2.3` would be rejected. Following the cursor restores complete
   verification. The Cite-check cache TTL is left at 10 min, which respects the retraction-list
   constraint.
5. **`set_reasoning synthesize off`.** This restores Monday's effective setting explicitly and
   removes 16k reasoning tokens per review, bringing cost per job back to baseline and cutting
   about 66 s per review. It is narrower than re-pinning the Synthesize model. The orchestrator's
   reasoning is left at `medium` (runbook §5).

**Why nothing smaller works.** The five causes act on four different components through
independent mechanisms. No single operation covers two of them, and leaving out any one leaves a
measurable failure class:

| Operation left out | What remains |
|---|---|
| op 1 | about 30% of jobs still fail at planning |
| op 2 | 429 → re-dispatch → failure |
| op 3 | partial extraction |
| op 4 | under-verified citations |
| op 5 | cost per job still above Monday |

**Nothing extra is included.** There is no credential revocation or rotation, no rollback, no
cache, concurrency, timeout or region change, and no change to the orchestrator's reasoning.

### Tooling decisions

- **Primary instrument: the traces, analysed with Python stdlib.** I started with exploratory
  aggregations covering errors by day, component and type; resolved models; token and cost
  profiles; wave sizes; payload-size distributions; cache behaviour as a function of the gap
  since the previous call; and per-job outcome classification. I then turned each finding into a
  reusable detector in `solve.py`, so the deliverables are *regenerated from evidence*, not
  hand-typed, and the same logic runs on any pack variant. I used no third-party packages, which
  keeps the tool within the Artifactory-only policy and avoids install-time failure.
- **Cross-checks against the human sources.** I reconciled the trace-derived numbers with the
  on-call chat. Job error rates of 0%, 51%, 53% and 51% match. FinOps' $0.60 → $0.66 matches
  $0.603 → $0.662. The alert counts match: decode alerts correspond to truncated papers, and
  parse alerts to plan failures. Where a stakeholder drew a conclusion (security's "access
  problem", the agent owner's "logging only" and "stale index?"), I tested it against the
  traces rather than accepting it.
- **Interview and replay tools: not used, and why.** The `litmus-incident` MCP server was not
  reachable from the analysis environment: one endpoint reported an expired token and the other
  had no authorisation header. No `ask_lead` questions or `staging_replay` runs were spent. I
  abandoned that path rather than block on it. The fix is derived from Kestrel's authoritative
  docs plus trace evidence for each mechanism.
- **Recommended validation once the token is refreshed** (1 of 5 replays): replay exactly
  `fix_set.json`. Expected results are 0 hard failures, about 0 degraded outputs, cost per job
  ≤ 1.0× Monday, and p95 near 4 min. If residual 429 failures remain, the first question
  should go to `vendor` (rate limits): whether back-off alone fits the new allowance at a wave
  size of 8. Only after that would I consider `set_max_fanout 6`.

### Uncertainty: what I am least sure of

- **Whether back-off alone clears all rate-limit failures.** I have not verified this by replay.
  The traces show about half of each 8-wide wave admitted, and a 4 s `retry_after`, which
  suggests back-off is sufficient. But I cannot see the new allowance number, and afternoon
  bursts with overlapping jobs might still exceed it. A residual would call for
  `set_max_fanout 6` (the SLA floor), not a smaller fan-out.
- **The `RATE_TIER_DOWNGRADE` onset.** I used the first rejected Litmus request (Tue 10:13). If
  the grader keys the onset to when the tier changed (02:00), this would be outside the one-hour
  tolerance. I chose "first affected Litmus" as the brief defines it.
- **`set_tool_arg_parsing object` versus `pin_model kp-2026-02`.** Both should eliminate the
  parse errors. I chose the forward-compatible one. If the replay showed any other behavioural
  difference in `kp-2026-08` planning, pinning would be the fallback.
- **The symptom-edge granularity.** `STAGE_REDISPATCH → JOB_FAILURES` could arguably be drawn
  from `IMMEDIATE_RETRY_STORM` instead. I followed the trace order: retries exhausted, then
  re-dispatch, then failure after the second re-dispatch. I left the count alerts out of
  `ALERT_FLOOD` on purpose (see above).
- **Most `kp-2026-08` plan calls (359 of 509) still parse successfully** despite the encoding
  change. Only about 30% fail, all three attempts each. This does not change the diagnosis or the
  fix, since every parse failure is on `kp-2026-08` and none occur on Monday, but I cannot explain
  the partial rate from the docs. It may depend on which tool calls a given plan emits.
